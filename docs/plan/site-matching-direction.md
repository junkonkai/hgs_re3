# HGN全体の方針：ゲームとの出会い・人とのつながり

作成日: 2026-09-11
状態: サイト全体の方向性を検討するための引き継ぎ資料。実装仕様・名称の確定ではない。

2026-09-12更新：続きの相談で合意した方針は第9節を参照。以前の提案をすべて採用したわけではない。レビュー入力と表示を検討する単独HTMLの試作を承認済み。サイト本体への実装は対象外。

## 1. ユーザーが提示した方向性

HGNの目指すところを、次の2種類のマッチングとして考える。

1. **ユーザーとゲーム**：自分の好みや楽しみ方に合うホラーゲームに出会う。
2. **ユーザーとユーザー**：好みやゲーム体験を手掛かりに、人とつながる。

この観点から「ゲームを探す」「フォロー」「レビュー」といった表現や、各機能の役割を見直してもよいのではないか、という問題提起があった。

レビューの個別設計を超えるため、サイト全体の方針は別チャットで検討を続ける。現時点では改称・画面変更・実装の指示はない。

## 2. この方向性に至った背景

レビューを「他人におすすめするか」「平均点はいくつか」から、「自分には合ったか」「どんな好みの人が、何を楽しんだか」へ見直す相談から始まった。

- 好みが異なる人の評価を平均すると、一部の人に強く刺さる理由が見えにくい。
- 総合点を主役から外す、または置かない案を検討している。廃止や既存データ移行は未決定。
- 怖さメーターは優劣ではなく体験の強さを伝える情報として、独立して扱う案。
- ゲームの楽しみ方、ホラー表現の好き嫌い、怖さへの耐性は同一ではない。
- 同じ作品に対して「全体として合った」と「戦闘には不満がある」が両立する。
- 人の好みが分かると、否定的な感想も別の人の作品選びに役立つ。

したがってレビューは、作品について知る入口であると同時に、感想を書いた人を知る入口にもなる。

## 3. 2種類のマッチングをつなぐ体験の案

ゲームを見つける → 感想を読む → 書き手の好みや視点に興味を持つ → その人の好きな作品や投稿から別のゲームを見つける。

逆に、人を入口としてゲームに出会う流れも考える。検索・レビュー・プロフィール・フォローを、この往復を支える機能として整理する案。

「マッチング」は現段階の設計上の呼び方であり、公開画面で使う用語や、数値の相性スコアを必須にする意味ではない。

## 4. 前チャットでの提案（未採用の文言候補）

サイトの価値を説明する言葉と、操作の意味を伝える言葉を分ける。

| 対象 | 価値を伝える文言の候補 | 操作・機能名の候補 |
|---|---|---|
| ゲームの発見 | 自分に合うゲームに出会う | ゲームを探す／好みから探す |
| 人の発見 | 好みがつながる人に出会う | 好みが近い人を探す |
| フォロー | 気になる人から、次のゲームへ | フォローする |
| レビュー | あなたの体験が、誰かのゲーム選びに | 感想を書く／体験を残す |

全体を表す候補として「好きなホラーゲームと、気になる人に出会う」も挙がった。いずれもアシスタントの提案であり、ユーザーが名称として採用したわけではない。

### フォローと好みの近さを同一視しない

好みが近くてもフォローしたいとは限らず、好みが違っても文章・知識・遊び方に興味を持つことがある。「フォロー」の機能が同じなら操作名は残し、周囲の説明を変える案を提示した。

人とのつながりには、少なくとも次の可能性がある。

- 好みが近く、作品選びの参考になる人。
- 好みが違い、知らなかった作品を教えてくれる人。
- 感想や遊び方に興味を持った人。

これらも検討のための提案であり、人の推薦条件として確定していない。

## 5. 好みを集める方針との関係

ユーザーからは、設問が大量にあっても、いつでも好きに答えられるならよいという考えが示された。

- タイトル詳細で「好き」「苦手」を押し、タイトルの情報に関連する追加質問を少数提示する。
- 追加回答や文章入力は任意。設定画面からまとめて回答する入口も用意する案。
- タイトルの情報は質問選定に使う。「作品が好き」から含まれる全要素を好きと自動登録しない。
- 設定画面で本人が明示した好みは、自動処理で変更しない。
- 作品単位の反応、普段の好み、AIによる推測、閲覧履歴を別に扱う。
- AIでレビューから情報を抽出する構想がある。毎回確認せず推測として保存する案と、本人に確認して好みに反映する案を区別する。
- 閲覧履歴はまず関心や質問選定の補助にする案。閲覧を好き嫌いと同一視しない。

初期版は明示された選択回答を比較材料にし、自由文は人が読む補足として使う提案。AI・履歴の具体的な導入時期や計算への反映は未決定。

ユーザー同士の好みの近さと、ユーザーとゲームの適合は別に設計する。未回答を不一致として扱わず、比較根拠と情報量が分かるようにする案。

## 6. 次のチャットで考える順番の提案

1. **提供価値**：2種類のマッチングによって、利用者にどんな出会いや判断を提供したいか。
2. **代表的な利用の流れ**：ゲームから人へ、人からゲームへ。未登録・回答なしでも成立する入口。
3. **各機能の役割**：検索、タイトル詳細、感想、プロフィール、フォローが何を担うか。
4. **表現と情報の配置**：サイト全体の説明、ナビゲーション、操作名。親しみやすさと意味の分かりやすさ。
5. **段階的な実現範囲**：現状との差分、少ないデータで成立する構成、後続の推薦機能。

名称だけを先に決めず、機能の役割と利用の流れを先に整理する提案。レビュー項目やアルゴリズムの細部へ直ちに戻る必要はない。

## 7. 未決定事項

- サイトのミッション・公開コピー・各機能名。
- 疎なつながりを支えるフォローの具体的な表示・通知・外部誘導の方法（距離感は第9節で合意）。
- 相性を数値で出すか、共通点や具体的な理由で示すか。
- 全体評価・平均点を廃止するか、既存データをどう扱うか。
- 「好き・苦手」と「合った・合わなかった」の意味と使い分け。
- 推測情報の公開範囲、修正方法、履歴利用の設定。
- 実装の範囲と順番。

## 9. 続きの相談で合意した方針（2026-09-12）

### ユーザーが明示した方向性

- ユーザーとゲームのつながりは密、ユーザーとユーザーのつながりは疎にする。
- サイト内で会話・交流の場を設けることは考えていない。レビューへのいいね程度の軽い関わりを想定する。
- 交流したい人へのXやSteamコミュニティ等への誘導は候補。日記は将来案であり、採用は未決定。
- 遊びたいゲームを探す際には、ゲーム性と怖さを含めた「ホラーゲームとしての面白さ」を知りたい。
- 作品タグは基本的に運営者が付け、レビュー的な機能からユーザーも関われるようにしたい。既存データの整理ではAIの補助も希望している。

### 提案に対してユーザーが合意したこと

- ゲーム詳細に「体験ごとに整理したレビューへの入口」を置く。
- レビューは選択式と任意の自由文を組み合わせる。
- 運営タグは作品にある要素、レビューの選択は本人の体験を表す。同じ要素で結び付けるが、情報の意味を分ける。
- 未登録の要素はユーザーが追加候補として提案できる方向。作品タグへの反映方法は未決定。
- 大きな要素だけでも回答でき、細かい選択と文章は任意にする五項目の入力案を、試作の土台にする。

入力案と合意・仮仕様の境界は [レビュー体験入力・画面設計](new-review/review-experience-screen-design.md) にまとめる。

### 引き続き提案・未決定のもの

- 「怖さと遊びが結び付く面白さ」という整理や、体験から探す入口、理由付き関連作品、作品ごとの問いと回答は、アシスタントの提案。
- AIによる体験別要約は候補。採用方法、更新・検証、少数意見の扱い、公開範囲は未決定。要約する場合に選択回答から理由を捏造しないこと、原文・書き手へ戻れることを設計上の確認点とする。
- 今回の試作では総合点・相性点・怖さ強度を扱わないが、既存機能の廃止を意味しない。
- サイトの公開コピー、各機能名、運営タグの正式体系、投稿データの公開・保存仕様は未決定。

### 今回の作業範囲

ユーザーの依頼により、GPT-5.6 Solのサブエージェントが単独HTMLの試作を担当し、親エージェントが設計資料整理と実装後のレビューを担当する。本番画面、DB、API、実AI処理は変更しない。
