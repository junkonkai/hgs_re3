## この資料の位置付け

レビュー設計についての相談内容と、次に深掘りする順番をまとめた資料。実装仕様の確定や変更の実行を意味しない。

既存の計画は [review-feature.md](../review-feature.md) と [review-implementation.md](../review-implementation.md) にある。本資料は、それらの総合点を中心とする設計を見直すための検討資料であり、既存資料に記載された実装状況は今回検証していない。

以下では、ユーザーから挙がった方向性と、会話中の提案・未決定事項を区別する。選択肢や表示文言は例であり、確定した公開文言ではない。

## 1. ユーザーから挙がった方向性

- 「おすすめするか」より「自分に合っているか」を軸にする。
- レビュー者の好みを可視化し、読む人が自分との共通点を手掛かりに判断できるようにする。
- 登録時や登録後のアンケートで、好みや楽しみ方を聞き取る。
- 本人の回答と実際のレビューを組み合わせ、その人の好みと各ゲームの体験を結び付ける。
- 好みが合う人と合わない人をまとめた総合点・平均点は、この方向性では意味が薄くなるのではないか。
- 怖さメーターは残す意味がありそう。ただし、継続や表示方法は未確定。

## 2. 提供したい価値

読む人が「どんな好みの人に、何が合った／合わなかったのか」を理解し、自分が遊ぶかどうかを判断できること。

同じ特徴でも、好みによって受け止め方は異なる。例えば「反撃できないこと」は、ある人には恐怖の魅力であり、別の人にはストレスになる。「合わなかった」という感想も、読む人にとっては興味を持つ材料になり得る。

「おすすめ」を「合った」に置き換えるだけでは十分ではない。好み・理由・作品の特徴を一緒に示すことが重要。

## 3. 好みを捉える情報

| 情報 | 例 | 役割 |
|---|---|---|
| 本人が申告する好み | 探索が好き、戦闘が好き、物語を重視する | レビューが少ない段階の手掛かり |
| 各作品での体験と反応 | 追跡は楽しかったが、やり直しの多さは苦手だった | 好みを具体化する材料 |
| 蓄積から推測する傾向 | 追われる緊張は好きだが、繰り返しの試行は好まない | 条件を含む好みの理解 |

「アクション好き」だけでなく、爽快な戦闘、厳しい資源管理、探索と戦闘のバランスなど、何を楽しむかまで捉えたい。

### アンケートについての提案

- 登録時は任意の短い質問から始め、後から回答・編集できるようにする。
- 好きな作品と、その作品の何が好きかを聞く。
- ホラーで楽しみたい体験、試行錯誤とテンポへの好み、求める怖さなどを聞く。
- 探索も戦闘も好きな人がいるため、不必要な二者択一にしない。
- レビュー時にも「今回どこが合ったか」を聞き、少しずつ情報を補えるようにする。
- パーソナリティの範囲は未決定。提案としては、ゲーム選びに関係する価値観・楽しみ方を中心とし、性格から好みを短絡的に推測しない。

### 混同しない情報

- **ゲームの特徴と好み**：「追跡が多い」と「追跡が楽しかった」は別。
- **耐性と好み**：ゴア表現が平気なことと、ゴア表現が好きなことは別。
- **遊んだ量と好み**：多く遊んだジャンルが、必ずしも好きなジャンルとは限らない。
- **申告と推測**：レビュー分析から得た傾向は、本人が選んだ好みと区別する。
- **好みの不一致と遊べなかった事情**：難しさ、不具合、プレイ環境なども理由として区別できるようにする。

推測した傾向で本人のプロフィールを勝手に上書きせず、確認・修正できる形を提案した。時間による変化や、その作品だけの例外も考慮が必要。

## 4. レビューと可視化の案

レビューの入力案は「合った／どちらともいえない／合わなかった」と、合った点・合わなかった点の文章。段階数、必須項目、評価なしの文章投稿を許容するかは未決定。

レビューカードでは、次の組み合わせを提案した。

- レビュー者の好みタグ。
- お気に入り作品の画像・作品名。
- 対象作品が自分に合ったかと、その理由。
- 閲覧者との共通点（共通して「合った」とした作品など）。

未登録の閲覧者でも、レビュー者の好みと好きな作品から判断できることを重視する。

初期の可視化はタグと作品画像を中心とする案。レーダーチャートは軸と数値の意味を定義してから検討する。プレイ記録のグラフを出す場合は「プレイ傾向」として、好みの申告と区別する。

「相性92％」などの数値は必須ではない。共通する作品や好みを根拠として示す方法を優先する案。好みが近いことは、そのゲームが合う保証ではなく、異なる感想にもアクセスできるようにする。

## 5. 総合点・平均点の扱い

平均点には「投稿者全体にどの程度好まれたか」という意味はあるが、「自分に合うか」とは異なる。全員がほどほどに好む作品と、一部の人に強く刺さる作品が、同じ平均点になり得る。

会話では、総合点を主役から外し、置かない方向を提案した。ただし、廃止の確定、個人の点数の扱い、既存データの移行方法は未決定。

代わりに、次の情報を中心にする案がある。

- 合った人・合わなかった人が挙げた理由。
- それぞれのレビュー者の好み。
- 自分と好みが近い人の感想。
- 怖さや体験の分布。

全体の「合った率」を大きく表示すると、好評率を競う構造に戻る可能性がある。「あなたとの相性点」も、総合点の代用品として必ず用意する必要はない。

集計や要約を表示する場合は、根拠の投稿数と元レビューを確認できるようにする。少数の投稿から「探索好きには合う」と一般化しない。

## 6. 怖さメーターの位置付け

作品の優劣ではなく、体験の強さを伝えるものとして継続する案。

- 怖さも個人差があるため、平均だけでなく分布を見せる。
- 突然の驚き、追われる緊張、じわじわした不安など、種類を添えることを検討する。
- 感じた怖さの強さと、その怖さを楽しめたかを分ける。
- 怖さが強いほど作品として高評価、という換算を前提にしない。

既存メーターとの整合、入力負担、集計方法は今後検討する。

## 8. 深掘りする順番の提案

画面や計算方法の前に、何を判断できるようにするか、何を記録するかを決める。

| 順番 | 検討テーマ | 決めること・成果物 |
|---|---|---|
| 1 | レビューの役割と評価の意味 | 読者が判断したいこと。「合った」の意味。総合点を廃止するか、個人の点数も見直すか |
| 2 | 好み・ゲーム体験の軸 | 何を好みとして扱うか。特徴、好き嫌い、耐性、怖さをどう分けるか。具体的な作品・人物例で整理 |
| 3 | 情報の集め方 | 登録時・登録後の質問とレビュー項目。必須／任意、回答負担、変更・公開範囲 |
| 4 | 読む画面と可視化 | ゲームページ、レビューカード、プロフィールで何を示すか。未登録・未回答・投稿が少ない場合も含む表示例 |
| 5 | 好みとレビューの結び付け方 | 共通点・類似性の根拠。申告と推測が異なる場合、変化、少数データへの対応。自動分析の必要性 |
| 6 | 集計と発見 | 怖さの分布、理由別の集計、レビューの並び順。異なる好みや未知の作品に出会う余地 |
| 7 | 最小構成と既存機能からの移行 | 初期対象、後回しにする機能、既存点数・レビュー・統計・関連表示への影響、検証方法 |

### 次回の出発点

まずは「合った」とは、好きだったこと、楽しめたこと、期待した体験ができたことのどれを指すのかを、具体例で整理する。

例として「怖すぎて中断したが忘れられない」「完成度は高いと思うが自分の好みではない」「不満は多いがとても好き」などを、どう表現できるべきか考える。ここが曖昧なままアンケートや相性計算を決めると、意味の異なる回答を混ぜてしまう。

### 初期構成の候補（未確定）

1. 任意の短い好みアンケートとお気に入り作品。
2. レビューの「合った／合わなかった理由」。
3. レビュー者の好みと、閲覧者との具体的な共通点の表示。
4. 怖さメーターの役割・表示の整理。

文章の自動分析、高度な相性計算、自動要約は後続候補とする。初期段階では「レビュー者の好みが見えることで、ゲームを選びやすくなるか」と「無理なく投稿できるか」を確かめる。
